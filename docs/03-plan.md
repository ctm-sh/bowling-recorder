# 03. 구현 계획

## 기술 구조
- **Next.js (App Router) + TypeScript + Tailwind CSS**: 모바일 우선 웹앱
- **Supabase (Postgres)**: 데이터 저장. 서버 액션에서 service key로만 접근하고, 브라우저에서 DB에 직접 접근하지 않는다.
- **인증**: 조회 화면은 공개. 운영진 화면과 모든 쓰기 작업은 공용 비밀번호 → 서명된 httpOnly 쿠키로 보호(미들웨어 + 서버 액션에서 이중 확인). 회원의 "나는 누구"는 쿠키 `me`에 member_id만 저장 (권한에는 쓰지 않음).
- **구글 시트**: 서비스 계정 + `googleapis`. 정모를 마감할 때 3개 탭을 덮어쓰기로 갱신.
- **테스트**: Vitest (도메인 계산은 전부 순수 함수로 만들고 테스트한다)
- **배포**: GitHub + Vercel

```
app/            화면 (홈, 정모, 회원, 설정, 로그인)
components/     공용 UI (하단 탭, 팀 카드, 스코어보드)
lib/domain/     순수 계산 로직 (에버, 팀 배분, 핸디, 순위, 정산, 상대 전적)
lib/db/         Supabase 쿼리
lib/sheets/     구글 시트 내보내기
scripts/        기존 엑셀 가져오기
supabase/       마이그레이션 SQL
```

## 스키마 (데이터 모델이 3개 이상이라 명시)
| 테이블 | 주요 컬럼 |
|---|---|
| members | id, name, tier(0~14), active, memo |
| sessions | id, date, fee_per_game(기본 2800), closed_at |
| attendees | session_id, member_id |
| games | id, session_id, game_no |
| teams | id, game_id, team_no, handicap, handicap_default, fill_score, fill_score_default (값 ≠ 기본값이면 "합의 조정" 표시) |
| team_members | team_id, member_id, tier_snapshot, handicap_snapshot, **group_no**(배분 묶음 = 상대방 그룹) |
| scores | id, member_id, game_id(nullable: 엑셀에서 가져온 기록), score, seq |
| tier_changes | member_id, from_tier, to_tier, reason, created_at |
| settings | handicap_table(json), default_fee, recent_n(20), sheet_id |

- 에버, 순위, 정산 금액은 저장하지 않고 점수에서 계산한다.
- 팀 핸디와 티어는 **게임 확정 시점 값으로 스냅샷**을 남겨, 나중에 티어가 바뀌어도 과거 정산이 바뀌지 않게 한다.

## 핵심 계산 규칙 (lib/domain)
1. **팀 배분**: 참석자를 에버 순으로 정렬하고 팀 수만큼씩 묶는다. 각 묶음을 팀별로 랜덤 배정하고, 남는 인원은 랜덤 팀에 넣는다(팀 인원 차이는 최대 1명). 묶음 번호(group_no)를 저장한다. 수동으로 이동할 때는 같은 묶음 안에서 맞바꾸는 것을 기본으로 한다.
2. **핸디**: 같은 묶음(상대방) 안에서 핸디표 값이 가장 작은 사람을 0으로 두고 각자 그 차이만큼 받는다 (team_members.handicap_snapshot). 팀 핸디 기본값 = 팀원이 받은 핸디의 합.
3. **팀 점수**: 팀원 점수 합 + 순 핸디(teams.handicap). 순 핸디 = (팀원 핸디 합 + 꼭두각시 점수) - 팀 중 최솟값. 꼭두각시 점수(teams.fill_score)는 마지막 묶음에서 상대가 없던 사람의 전체 에버(여러 명이면 평균, 정수 반올림). 순 핸디는 합의에 따라 운영진이 덮어쓸 수 있다.
   - 직접 구성 모드: 각 팀을 에버 순으로 정렬해 같은 순번끼리 group_no를 부여하고, 운영진이 수정할 수 있다.
4. **순위**: 팀 점수 내림차순. 동점이면 핸디가 큰 팀이 아래 순위, 그래도 같으면 실제 점수가 낮은 팀이 아래 순위.
5. **정산**: 1등↔꼴찌, 2등↔뒤에서 2등 순으로 짝을 짓는다. 아래 순위 팀이 (대신 내는 인원 + 자기 팀 인원) × 게임비를 내고, 짝이 없는 가운데 팀은 자기 몫만 낸다. 대신 내는 인원은 min(위 팀 인원, 아래 팀 인원)이다. 위 팀에서 남는 인원은 개인 점수 + 개인 핸디가 낮은 순으로 자기 몫을 직접 낸다. 아래 팀에서 남는 인원은 개인 점수 + 개인 핸디가 높은 순으로 자기 몫만 낸다. 팀원끼리 1/N로 나누고 100원 단위로 올림한다.
6. **개인 승률**: 팀이 1등이면 승, 나머지는 패.
7. **상대 전적**: 같은 게임에서 같은 group_no였던 사람끼리만 개인 점수 + 개인 핸디로 비교한 승·패·무. 핸디는 따로 표시한다.

## 각 M 상세
**M1** 할 일: Next.js 생성, Tailwind, Supabase 프로젝트와 마이그레이션, 운영진 공용 비밀번호 쿠키 인증, 회원용·운영진용 하단 탭 레이아웃.
검증: `npm run build` 성공 / 수동: 로그인 없이 회원 탭이 보이고, 운영진 화면 URL은 로그인으로 리다이렉트된다.

**M2** 할 일: `lib/domain`의 계산 규칙 1~7 구현.
검증: Vitest. 2팀·3팀·4팀 정산, 4·4·3에서 1등 팀 개인 꼴찌의 자기 부담, 상대 없던 사람 에버로 인원 보정, 인원 차이 2명 이상 형태 거부, 동점(핸디 큰 팀 패), 100원 올림, 나누어떨어지지 않는 배분과 group_no, 승률(1등만 승), 같은 묶음끼리만 상대 전적.

**M3** 할 일: `scripts/import-xlsx`로 `점수기록지`, `티어표`, `핸디` 시트 가져오기 (점수에는 날짜가 없어 game_id 없이 순서만 저장). 회원 목록, 추가·수정·비활성.
검증: 회원 수 44명, 총 게임 534, 김철수 에버 207.1 일치.

**M4** 할 일: 정모 생성 (날짜, 게임비 기본 2,800원, 수정 가능), 최근 참석자가 위에 오는 참석 체크.
검증: 수동: 휴대폰 폭에서 11명 체크 후 정모 화면 진입.

**M5** 할 일: 인원에 맞는 형태 추천 (2팀, 3팀, 개인전 등), **랜덤 / 직접 구성** 모드, 다시 섞기, 팀 간 이동, 상대방(묶음) 표시·수정, 팀별 핸디·보정 점수 수정(기본값과 "합의 조정" 표시), "팀 그대로"로 다음 게임 생성.
검증: 수동: 11명을 4·4·3으로 랜덤 배정, 직접 구성으로도 배정, 핸디를 합의값으로 바꾸고 결과 계산에 반영되는지 확인.

**M6** 할 일: 팀 카드별 큰 숫자 입력칸, 자동 포커스 이동, 팀 합계와 핸디 표시, 0~300 범위 검증, 입력 즉시 저장.
검증: 수동: 휴대폰 키패드로 11명 입력, 새로고침해도 유지.

**M7** 할 일: 결과 화면 스코어보드와 팀 카드 스와이프, 패배 팀과 1인 부담금 강조, [팀 그대로][섞기][마감] 버튼, 정모 마감 시 사람별 합계와 카톡 공유용 텍스트 복사.
검증: 수동: 3게임 진행 후 정산 합계를 손으로 계산한 값과 비교.

**M8** 할 일: 회원 상세 (전체 에버, 최근 N게임 에버와 차이, 티어별 상대 전적, 티어 이력), 승급·강등 후보 배지 (최근 폼이 현재 티어 평균과 위아래 티어 경계를 넘을 때), 티어 변경 시 **사유 필수 입력**.
검증: 수동: S3 재현. 사유 없이는 변경 불가.

**M9** 할 일: "나는 누구" 이름 선택(기기별 쿠키 `me`, 변경 가능 — 서버에서 바로 개인화하려고 localStorage 대신 쿠키), 홈 내 요약(최근 정모 점수·팀 순위·낼 금액), 정모 목록과 상세(B 스코어보드 조회 전용, 전체 점수표, 정산), 내 기록(에버·최근 폼·승률·최근 게임), 상대별 전적(점수+핸디, 핸디 별도 표시), 랭킹. 조회 화면에는 수정 버튼이 노출되지 않는다.
검증: 수동: 시크릿 창에서 S4 재현. 서버 액션을 직접 호출해도 쓰기 거부.

**M10** 할 일: 설정 화면 (핸디표 편집, 기본 게임비, 최근 N게임), 구글 서비스 계정 연동, 마감 시 `점수기록`·`회원현황`·`정산` 탭 갱신, 수동 재동기화 버튼.
검증: 수동: 마감 후 구글 시트에 행이 반영됨.

**M11** 할 일: Vercel 배포, 환경 변수, README, 최종 QA 체크리스트 (자동 검증, S1~S4, 모바일, 엣지 케이스, 마감 정리).

## 차별점 반영 위치
"점수 + 최근 폼 + 상대 전적을 근거로 보여주고 운영진 결정 사유를 남긴다"
→ 상대 전적 계산은 **M2 할 일 7**, 운영진 화면과 사유 필수 입력은 **M8 할 일과 완료 조건**, 회원에게도 같은 근거를 공개하는 것은 **M9**.
